# Technical Product Company OS

Read `references/TECHNICAL_PRODUCT_COMPANY_OS_CONTRACT.md` before changing
portfolio scope, routing, telemetry, authority, automations, or improvement.
Read `references/PROJECT_POSITION_AND_COMPLETION_CONTRACT.md` when an existing
project, partial build, repair, integration, or finish line is unclear.

## Diagnose before scaling

When an existing work item's position, purpose, destination, completion depth,
acceptance boundary, or integration target is materially unclear, run the
project-position diagnostician before product catalysis, project management, or
a delivery workflow. Suppress it for a fresh approved control packet or an exact
bounded task. Separate bounded observed
position from Lowell's desired destination. Diagnose working, broken, incomplete,
dependency, validation, integration, MCP-fit, UI/UX, and authority surfaces, then
ask at most three questions that materially change the route.

Record the durable end-state class and the completion depth for this engagement.
Do not infer either from repository activity. A major product may need only a
repair; a reusable artifact may be complete without productionization. Stop at
the human-confirmed sufficient condition and keep unneeded families and
specialist packs suppressed.

## Route

1. Establish the human goal, stable project identity, constraints, consequence,
   privacy class, requested decision right, and acceptance evidence.
2. Query the generated catalog. Apply authority, eligibility, lifecycle, tool,
   environment, privacy, and consequence gates before retrieval.
3. Combine exact triggers, lexical retrieval, optional semantic candidates,
   prior validated workflows, and dependency-graph expansion.
4. Return the smallest sufficient capability set with prerequisites,
   independent validators, alternatives, suppressors, and reason codes.
5. Keep considered, selected, executed, completed, and independently validated
   evidence distinct. Selection is not use.

## Shape and coordinate

Use the product catalyst to frame no-build, reuse, adapt, and build alternatives,
hypotheses, falsifiers, and the smallest safe experiment. It cannot set priority,
spend, contact users, collect data, or activate work.

Use the project manager only after the human approves the outcome and stable
identity. Compose `personal-project-management-ops`; do not create a parallel
state machine. Produce bounded workstreams, dependency order, WIP limits,
acceptance checkpoints, a decision log, the smallest next action, and a compact
resume capsule. Never invent deadlines or mutate Git, tasks, schedules, project
truth, releases, or external systems.

Use the Integration/MCP/Automation family and its MCP specialist pack only for
an explicit integration gap. Use the Product/UX/Accessibility family and its
UI/UX specialist pack only for a named human-facing design gap. Each pack is a
catalog of on-demand expertise; never activate every specialist by default.

## Govern decisions

Apply the decision-rights gateway: `observe`, `retrieve`, `recommend`, `draft`,
`validate`, `execute`, and `prohibited`. Rights do not rise with model strength.
Execution is denied unless a verified, exact, unexpired lease and all required
human, checker, domain, rollback, and final-confirmation gates exist.

## Automate economically

Prefer deterministic tools for exact work. Route large, simple, mechanically
verifiable packets to an approved low-cost batch or Cursor-style adapter only
after sanitization and an explicit scope lease. Keep routines delta-based,
deduplicated, budgeted, quiet on no-change, and dormant until human activation.
External adapters cannot install plugins, change global settings, capture data
persistently, access secrets, deploy, merge, or claim extra authority.

## Observe and improve

Compile a fingerprinted catalog from source-owned registries. Record privacy-safe
append-only receipts only when explicitly enabled. Never store raw prompts,
conversations, source rows, absolute paths, client data, secrets, or permanent
provider IDs.

Use the gap sentinel with `dad-trigger-pattern-radar`; use the improvement
steward with `subagent-continuous-improvement`. They may emit one deduplicated
candidate only: `no_change`, `observe_more`, `route_existing`,
`improve_candidate`, or `new_candidate`. They cannot rewrite, activate,
promote, suppress, supersede, retire, or execute.

Never treat frequency, recency, centrality, similarity, model output, provenance
completeness, or a self-grade as proof of value or correctness. Never-used means
`unobserved`, not stale. Keep synthetic trials outside operational metrics.
