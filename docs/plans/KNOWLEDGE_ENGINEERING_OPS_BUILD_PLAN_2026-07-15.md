# Knowledge Engineering Ops Build Plan

Status: approved by the user's explicit build request; local implementation
authorized; external adoption, recurring activation, and production mutation
remain separately human-gated.

## Outcome

Create one portable, provider-neutral Knowledge Engineering specialist family
that can diagnose, design, build, evaluate, operate, migrate, and retire:

- direct long-context and retrieval-free baselines;
- lexical, dense, hybrid, filtered, multi-stage, and reranked retrieval;
- fixed, structural, semantic, contextual, late, parent-child, and hierarchical
  chunking;
- vector indexes and vector-database adapters;
- property, RDF, provenance, event, temporal, GraphRAG, LightRAG, and graph-lite
  systems;
- agentic, corrective, and adaptive retrieval;
- source-governed ingestion, change-data capture, deletion, migration, and
  lifecycle operations;
- retrieval, answer, citation, graph, security, privacy, cost, latency, and
  recovery evaluation;
- a pointer-only weekly frontier research routine.

The portable skill is `knowledge-engineering-ops`. In DAD it is registered as
a specialist pack under `family:data-schema-knowledge-graph`, not as a third
overlapping top-level family. `family:knowledge-research-provenance` supplies
research authority and `family:quality-verification-release` supplies
independent assurance.

## Non-goals

- No universal vector database, embedding model, chunker, graph system, or LLM.
- No copying of Logos Scripture, Mock Trial case/client material, papers,
  transcripts, prompts, or external source bodies.
- No production corpus, index, ontology, ACL, deployment, or cross-repository
  mutation.
- No recurring schedule activation in this change.
- No provider or model identifier as durable role identity.

## Phases

### Phase 0: identity, authority, and reuse

Preserve the existing parent and peer family IDs. Register a child specialist
pack, stable skill ID, typed dependency edges, privacy boundaries, and an
independent checker. Use source pointers from DAD, Logos, and Mock Trial without
copying private or domain-authoritative content.

Acceptance: no duplicate top-level family; stable parent/peer relations and
source-authority limits are machine-readable.

### Phase 1: portable operating skill and role mesh

Build the runtime-neutral skill, role pack, preflight/midflight/postflight
contract, routines, and Codex interface metadata. Include router, authority
boss, architect, foreman, ingestion, chunking/context, retrieval/index,
long-context, graph-retrieval, evaluation, migration, writer, checker, and
frontier-sentinel responsibilities. Route by Luna/Terra/Sol capability classes
only at attempt time.

Acceptance: the same portable files validate in DAD and the global personal
skill root; one writer and a distinct checker are enforced.

### Phase 2: technique and source libraries

Create governed technique cards with applicability, contraindications, danger,
prerequisites, baselines, evaluation, operations, sources, and lifecycle.
Create a weekly primary-source watchlist covering standards, labs, original
papers, vector engines, evaluation, security, and ingestion.

Acceptance: every card is bounded and sourced; novelty, benchmark position, or
vendor claims cannot promote a technique.

### Phase 3: deterministic catalog, routing, graph, and research plan

Implement read-only commands for status, catalog search, evidence-based route
selection, transitive dependency inspection, and the inactive weekly research
plan. Deterministic routes must include direct-context and no-retrieval
baselines and fail closed on unsupported or ambiguous authority.

Acceptance: commands are read-only, schema validated, provider neutral, and
return candidate evidence rather than dispatch or execution authority.

### Phase 4: DAD and portable-global integration

Register schemas, skills, capabilities, offering, evaluation profile, family
membership, graph relations, and global-personal-skill allowlist metadata.
Install the portable skill into the live global personal skill root because the
user explicitly requested a global skill; retain that live root as runtime
source authority.

Acceptance: DAD discovers the capability by RAG, long-context, chunking,
vector, and graph terminology; the global skill is self-contained and contains
no local absolute paths.

### Phase 5: validation and independent review

Add synthetic schema, catalog, route, graph, research, portability, privacy,
and CLI tests. Validate the role pack, skill library, family portfolio, global
skill, DAD registry, and repository baseline. Run a fresh independent
red-team/checker pass and reconcile material findings.

Acceptance: focused tests pass; full validation has no new failure; producer
does not approve its own output.

### Phase 6: separately gated deployment

After merge, Lowell may separately approve: weekly schedule and delivery;
Logos and Mock Trial pointer adoption; real-corpus pilots; provider egress;
vector or graph infrastructure; and production cutover. Each requires its own
scope, authority, privacy, cost, rollback, and acceptance decision.

Acceptance: none of these effects occur merely because the family exists.

## Stop and rollback conditions

Stop on unknown source authority, sensitive content movement, unreviewed
embedding/provider egress, unsupported graph truth claims, writer/checker
collision, schedule activation, cross-repository write, or validation evidence
that cannot be reproduced. Roll back the branch/commit and remove the global
skill directory plus its allowlist row; immutable research pointers and review
evidence may remain for audit.
